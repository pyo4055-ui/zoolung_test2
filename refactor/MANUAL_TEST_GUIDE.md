# 수동 A/B 검증 가이드

## 비교 대상

- 운영본: GitHub Pages의 현재 `main`
- 리팩토링본: `refactor-preserve-behavior` 브랜치

> 비밀번호/계정 정보는 문서나 이슈에 기록하지 않는다.

## 1. 고객 예약 기본 동작

1. 운영본과 리팩토링본을 각각 연다.
2. 같은 조건으로 방문일/인원/입퇴장/식사/놀이터를 입력한다.
3. 무료 인솔자, 유료 인솔자, 금액, 예약 가능/불가 판단이 같은지 확인한다.
4. 동물원 안내/놀이터 안내/주차 안내 노출 시점과 내용이 같은지 확인한다.
5. 리팩토링본에서 테스트 예약 1건을 신규 등록한다.

기록: `고객 예약 OK / 이상: ...`

## 2. 관리자 예약

1. 리팩토링본 관리자 로그인.
2. 테스트 예약이 관리자 캘린더/예약현황에서 보이는지 확인.
3. 예약 확정.
4. 인원/입퇴장/식사/놀이터/특이사항 수정 후 저장.
5. 새로고침 후 값 유지 확인.
6. 접수일/예약일 조회 기준 확인.

기록: `관리자 예약 OK / 이상: ...`

## 3. 정산

1. 자체 또는 테스트용 아웃소싱 업체 지정.
2. 실제 유료/무료인솔/유료인솔/카페 결제금액 입력.
3. 계산된 매표매출/카페매출/수수료 확인.
4. 저장 후 새로고침.
5. 동일 금액으로 다시 표시되는지 확인.

기록: `정산 OK / 이상: ...`

## 4. 관리자 스케줄

1. 테스트 예약의 스케줄 관리 열기.
2. 4F/5F/식사/놀이터 시간 확인.
3. 겹침/종료<=시작/퇴장시간 초과 차단 확인.
4. 스케줄 반영.
5. 스케줄 확정.
6. 고객 예약조회에서 확정 스케줄 노출 확인.

기록: `관리자 스케줄 OK / 이상: ...`

## 5. 현장 스케줄

1. 리팩토링 현장스케줄에서 직원 로그인.
2. 테스트 예약 날짜로 이동.
3. 단체명/인원/전화번호/타임라인/컨텐츠 색상 확인.
4. 수정 가능 전환.
5. 실제 유료/인솔, 도착예정, 퇴장예정, 결제, 컬러북, 메모, 인상착의, 식사위치, 카페내용 중 테스트 값을 입력.
6. 컨텐츠 시간 변경 후 저장.
7. 공용 메모는 수정 잠금을 다시 잠근 뒤에도 수정 가능한지 확인.
8. 새로고침 후 값 유지 확인.
9. 고객 예약 원본의 예약 정보가 현장 수정 때문에 바뀌지 않았는지 확인.

기록: `현장 스케줄 OK / 이상: ...`

## 6. 엑셀 4종

각각 운영본과 리팩토링본에서 동일 조회조건으로 내려받는다.

- 예약현황
- 식사관리
- 아웃소싱 결제대금
- 스케줄관리

열 순서, 병합, 합계, 금액, 표시값, 파일 열림 여부를 비교한다.

기록: `엑셀 4종 OK / 이상: ...`

## 완료 기준

모든 항목이 OK이고, Firestore 저장 후 새로고침/다른 화면에서도 동일하게 보이며, 현장 수정이 원본 예약에 역반영되지 않아야 한다.

하나라도 이상하면 `main` 병합 금지.
